# Connect.dev testing and evaluation guide

This repository uses a low-resource local test path and moves the expensive browser matrix and repeated performance runs to GitHub Actions. Local tests use an isolated MongoDB database ending in `_test` and a separate Redis namespace. The safety guard refuses to reset a remote database or a database without the `_test` suffix.

## 1. What is installed and what it costs

Approximate sizes vary by npm and Docker version. Check the real usage with the commands in the last column.

| Component | Needed locally? | Approximate SSD use | Runtime memory | How to verify |
|---|---|---:|---:|---|
| Root, client, and server `node_modules` | Yes | about 337 MB in this checkout | 300-900 MB while testing | `Get-ChildItem node_modules,client\node_modules,server\node_modules -Recurse -File \| Measure-Object Length -Sum` |
| MongoDB 8 Docker image | Only for integration/performance | 1.28 GB measured on this PC | capped at 768 MB | `docker system df -v` |
| Redis Alpine Docker image | Only for Redis/realtime/performance | 57.3 MB measured on this PC | capped at 128 MB; Redis data capped at 64 MB | `docker system df -v` |
| Mongo test volume | Only while test data is retained | 212 MB measured after the functional seed | included in Mongo limit | `docker system df -v` |
| Playwright Chromium | No; CI installs it | commonly 300-450 MB | about 500 MB-1 GB while running | `npx playwright install --list` |
| Firefox and WebKit | No; nightly CI only | commonly another 500 MB-1 GB | not used locally | GitHub Actions artifact/report |
| k6 | No; nightly CI uses its container | no local project storage | not used locally | GitHub Actions performance artifact |

The Compose file caps the two database containers at 896 MB combined and 1.5 CPUs combined. Docker Desktop itself adds overhead, so allow roughly 1.3-2 GB of free RAM during integration tests. Unit tests do not require Docker.

Docker Desktop Kubernetes is enabled on this PC and starts a separate Kubernetes control plane plus unrelated application containers. Those resources are not required by Connect.dev and explain much of Docker's background load. If Kubernetes is not needed for other work, disable it in **Docker Desktop > Settings > Kubernetes**; do not delete its images or workloads until you confirm no other project needs them.

No Playwright browser binary or k6 image is required for the normal local path. Keep the Mongo and Redis images after a run if you expect to test again; removing images saves SSD space but forces another download.

## 2. Credentials and secret handling

All values below are test-only and are safe to replace. They must never be used for production.

| Purpose | Local test value |
|---|---|
| Seeded app email | `testuser0@example.test` |
| Seeded app password | `ConnectTestOnly!1` |
| Seeded usernames | `testuser0000` through `testuser0011` for the functional seed |
| Mongo username | `connect_test` |
| Mongo password | `connect_test_password` |
| Mongo address/database | `127.0.0.1:27018/connect_test` |
| Redis password | `connect_redis_test` |
| Redis address | `127.0.0.1:6380` |
| Test JWT secret | already defined in `server/.env.test.example`; test use only |

Automated tests do not need a real Stripe, Razorpay, Cloudinary, Render, GitHub, Gmail, or other third-party login. Payment unit/integration tests use test behavior and mock keys; they must never charge a real card.

Do not send a personal password, private key, API secret, or one-time code in chat, commit it to Git, or put it in `.env.test`. If a real sandbox integration is tested later:

1. Copy `server/.env.test.example` to the ignored file `server/.env.test.local`.
2. Put only sandbox/test-mode credentials in that file.
3. Confirm `git status --short` does not list that file.
4. Revoke or rotate the sandbox key after sharing a demo environment.

GitHub Actions itself does not require your GitHub password. After the workflow files are pushed, GitHub supplies the repository-scoped `GITHUB_TOKEN`. To push from a new PC, use browser/device authentication (`gh auth login`) or Git Credential Manager; never give the application or another person your GitHub password. The only optional repository secret currently referenced is `RENDER_DEPLOY_HOOK_URL`:

1. Open the GitHub repository.
2. Go to **Settings > Secrets and variables > Actions**.
3. Choose **New repository secret**.
4. Name it `RENDER_DEPLOY_HOOK_URL` and paste the deploy hook generated by Render.
5. If it is absent, CI prints a skip message and does not fail.

## 3. Fast local evaluation (no Docker)

Run these from the repository root in PowerShell.

```powershell
npm.cmd run test:unit
npm.cmd --prefix client run lint
npm.cmd --prefix client run build
```

Pass criteria:

- Server critical modules meet the configured coverage floor: 80% lines/statements/functions and 70% branches.
- Client critical modules meet the configured coverage floor: 80% lines/statements/functions and 70% branches.
- There are zero failed tests and zero ESLint errors.
- The Vite production build exits successfully. A bundle-size warning is a performance backlog item, not a functional failure.

This is the default pre-commit check and has the smallest SSD/RAM impact.

## 4. API, Redis, and realtime evaluation

### Start isolated services

Start Docker Desktop, then run:

```powershell
npm.cmd run test:services:up
```

The first Mongo pull is the largest one-time download. Later runs reuse the image.

### Run the service-backed suites

```powershell
npm.cmd run test:integration
npm.cmd run test:redis
npm.cmd run test:realtime
```

The suites verify:

- authentication and health/readiness endpoints against real MongoDB;
- Redis JSON cache behavior, corrupt-entry recovery, version invalidation, presence, helper-busy state, and batched lookups;
- authenticated Socket.IO connection and personal-room membership;
- that tests cannot erase a remote or non-test MongoDB database.

Pass criteria: every command exits with code 0, no suite is skipped unexpectedly, and readiness reports MongoDB healthy. Redis integration tests must use `127.0.0.1:6380`, never a production Redis URL.

### Stop services and release RAM

```powershell
npm.cmd run test:services:down
```

This removes only the Compose test containers, network, and the named test-data volume. It retains the Docker images so the next run does not download them again. Quit Docker Desktop afterward to release its background RAM.

To inspect disk use before deciding whether to delete an image:

```powershell
docker system df -v
```

Do not run a broad Docker prune if other projects use Docker. If space is urgently needed, remove only an explicitly named unused test image after confirming it is not used elsewhere.

## 5. Manual product regression checklist

Use two fresh test accounts or two separate browser profiles. Use an incognito profile with extensions disabled when checking console errors; `[BHK] widget sdk` and `runtime.lastError: message port closed` are generated by browser extensions, not Connect.dev.

### Payment-gated ticket visibility

1. Sign in as requester A and create a paid help ticket.
2. Confirm A sees the ticket in **Your active help requests** with `payment pending`.
3. Sign in as unrelated developer B before payment authorization.
4. Confirm B cannot see the ticket in matching requests or retrieve it through the feed API.
5. As A, select **Continue payment**.
6. Confirm the browser is redirected to the payment provider URL; the application must not repeatedly call `refresh-payment` and produce `409 Conflict` responses.
7. Complete the provider's test-mode authorization and return to the app.
8. Confirm A sees a successful payment-sync message and the ticket moves to the searchable/direct state.
9. Confirm B, or the intended direct helper, can now see the ticket.
10. Cancel the test ticket and verify it disappears from active feeds.

Pass criteria: unpaid paid tickets are visible only to their requester; the payment action redirects; authorized/free tickets follow their intended visibility; no first-party console errors occur.

### Dark-mode dialogs

1. Enable dark mode.
2. Open **Edit Profile**, **Schedule Live Event**, **Create Room**, and **Create Ticket**.
3. Check header, body, inputs, selected tags, borders, backdrop, scrollbar, close control, and focus ring.
4. Tab through every control and press Escape to close.
5. Repeat the smoke check in light mode.

Pass criteria: no light panel/text flashes in dark mode, all text has readable contrast, focus is trapped in the dialog, Escape closes it, and focus returns to the trigger.

### Developer filters

1. Seed functional data: `npm.cmd run test:seed`.
2. Sign in with the seeded app credential and open **Explore > Developers**.
3. Add `react`; verify only matching skills/stack/domain results appear.
4. Choose a specialization and experience level; verify the result set narrows.
5. Enable **Open to mentor**; verify each result is a mentor/instructor.
6. Remove filters individually, then use **Clear**; verify the default suggestions return.
7. Switch between **Suggested** and **Popular**; verify Popular changes ordering but preserves the active filtered set.

Pass criteria: each request contains the selected query parameters, stale slower responses do not overwrite the newest filters, and empty results show the filtered empty state.

### Realtime and responsive smoke checks

1. Open the same room as two users and exchange messages, reactions, typing state, and join/leave events.
2. Refresh one client and verify there is one live socket connection, not duplicate `connect` events.
3. Exercise the key pages at 360 px, 768 px, and desktop widths.
4. Confirm navigation, dialogs, ticket actions, and developer cards do not overflow or become unreachable.

## 6. Redis response-time comparison

The comparison is deliberately A/B/C rather than a single before/after sample:

- `mongo-only`: MongoDB without Redis.
- `redis-no-cache`: Redis connected for realtime/helper state, response cache disabled.
- `redis-cache`: Redis connected and short-lived feed/suggestion caches enabled.

Each mode uses identical seeded data, authenticated requests, virtual users, duration, and endpoint mix. A warm-up is excluded, three local repetitions (five in CI) are aggregated by median, and the report records p50, p95, p99, requests/second, and error rate.

The acceptance gate is:

- cached Redis median p95 is at least 30% faster than Mongo-only; and
- cached Redis request error rate is below 1%.

The standard low-disk choice is to run this in **GitHub Actions > Nightly quality suite > Run workflow** and download the small `redis-performance` artifact. The report is `redis-comparison.md`, with machine-readable data in `redis-comparison.json`.

If k6 is already installed locally, start the test services and run:

```powershell
npm.cmd run test:perf:compare
```

Do not download k6 solely for a one-time local run; use CI. The performance command reseeds the isolated test database with 1,000 users, 2,000 rooms, 2,000 issues, and 500 tickets, performs three repetitions per mode, then writes ignored output under `artifacts/performance/`.

Interpret the result carefully:

- Compare p95 first; averages hide slow-tail regressions.
- Compare `redis-no-cache` with `mongo-only` to see Redis connection/adapter overhead.
- Compare `redis-cache` with both baselines to isolate cache benefit.
- Reject a faster result if errors exceed 1% or data correctness/visibility differs.
- Re-run after a cold restart when a result is close to the 30% boundary.

## 7. Browser matrix in CI

Normal CI runs one Chromium regression to keep feedback quick. The nightly workflow runs desktop Chromium, Firefox, WebKit, Pixel 7, and iPhone 15 profiles. On failure, it retains traces, screenshots, video, and an HTML report.

To evaluate a pull request:

1. Push the branch and open the pull request.
2. Open the **Checks** tab.
3. Require **Client**, **Server**, **API, Redis, and realtime integration**, and **Chromium E2E** to pass.
4. Open failed job logs rather than rerunning blindly.
5. Download the Playwright artifact for any browser failure and inspect the trace/screenshot.
6. For release candidates, manually run **Nightly quality suite** and require both jobs to pass.
7. Review the Redis artifact and record its p95 improvement in the release notes.

## 8. Release scorecard

Use this scorecard for every release candidate:

| Area | Required result | Evidence |
|---|---|---|
| Unit correctness | 100% test pass; coverage gates pass | Vitest output/coverage summary |
| Code quality | 0 ESLint errors | Client CI log |
| Build | Client build and server image pass | CI logs |
| API/data | Integration suite passes against isolated Mongo | Integration CI log |
| Redis | Redis behavior and invalidation suite passes | Integration CI log |
| Realtime | Authenticated socket suite passes | Integration CI log |
| Payments | Unpaid visibility and redirect checklist pass | Tester, date, ticket IDs (never card data) |
| UI/theme | Light/dark dialogs pass keyboard and visual checks | Playwright artifact plus manual notes |
| Discovery | Tech/specialization/experience/mentor filters pass | Manual notes or network capture without tokens |
| Browsers | Chromium on PR; full matrix before release | GitHub check run |
| Performance | p95 improvement >=30%; errors <1% | Redis comparison artifact |
| Security | No production secret in Git; dependency audits have no high production findings | CI logs and secret review |

A release is accepted only when every required row passes. A failure needs an issue with an owner, severity, reproduction steps, and a conscious release-block/waiver decision. Never waive payment visibility, authentication, remote-database safety, or exposed-secret failures.

## 9. Full command sequence

For a machine with enough RAM and the Docker images already downloaded:

```powershell
npm.cmd run test:unit
npm.cmd --prefix client run lint
npm.cmd --prefix client run build
npm.cmd run test:services:up
npm.cmd run test:integration
npm.cmd run test:redis
npm.cmd run test:realtime
npm.cmd run test:services:down
```

Run the browser matrix and repeated Redis benchmark in GitHub Actions to avoid the largest optional local downloads.
